# מערכת להזמנת חדרי ישיבות

שרת: ASP.NET Core 8 (Minimal API). לקוח: Angular 19.
דף אחד שבו בוחרים חדר ותאריך, רואים את ההזמנות של אותו יום, מוסיפים הזמנה ומבטלים הזמנה.

## 1. הוראות הרצה

דרישות מוקדמות: ‎.NET 8 SDK ו-Node.js 20 ומעלה.

```bash
# טרמינל 1: שרת (http://localhost:5080)
cd server
dotnet run --project MeetingRooms.Api

# טרמינל 2: לקוח (http://localhost:4200)
cd client
npm install
npm start
```

פותחים את http://localhost:4200. שרת הפיתוח של Angular מעביר את כל הבקשות ל-`/api` אל השרת (`proxy.conf.json`), כך שאין צורך ב-CORS.

הרצת בדיקות:

```bash
cd server
dotnet test
```

### API

| Method | URL | תשובות |
|---|---|---|
| GET | `/api/rooms` | ‏200 |
| GET | `/api/bookings?roomId=1&date=2026-11-24` | ‏200 (ממוין לפי שעת התחלה), ‏400 (פרמטר חסר או לא תקין), ‏404 (חדר לא קיים) |
| POST | `/api/bookings` | ‏201, ‏400 (ולידציה או JSON לא תקין), ‏409 (חפיפה) |
| DELETE | `/api/bookings/{id}` | ‏204, ‏404 |

גוף בקשת POST:
```json
{ "roomId": 1, "title": "Standup", "start": "2026-11-24T09:00:00", "end": "2026-11-24T09:30:00", "bookedBy": "Dana" }
```
כל השגיאות מוחזרות בפורמט ProblemDetails (RFC 7807): `title` ו-`detail`, ובשגיאות ולידציה גם `errors` לפי שדה.

## 2. החלטות עיקריות

- **אחסון בזיכרון** (רשימה בתוך Singleton). כך אין צורך להתקין מסד נתונים כדי להריץ, וזה מספיק להיקף המבחן. החיסרון: הנתונים נמחקים בכל הפעלה מחדש של השרת.
- **בדיקת החפיפה וההוספה נעשות בתוך `lock` אחד**. בלי זה, שתי בקשות שמגיעות במקביל יכולות לעבור את הבדיקה ולהזמין את אותו זמן. יש לזה בדיקה ייעודית.
- **חפיפה מחושבת כטווח חצי-פתוח `[start, end)`**: `a.Start < b.End && b.Start < a.End`. לכן הזמנה שמסתיימת ב-10:00 והזמנה שמתחילה ב-10:00 לא חופפות.
- **חוקי העסק נמצאים ב-`BookingService` ולא ב-endpoints**. ה-service מחזיר תוצאה (Created, Invalid או Conflict), וה-endpoint רק ממפה אותה לקוד HTTP. כך אפשר לבדוק את החוקים בלי HTTP.
- **קודי סטטוס**: ‏400 לקלט לא תקין, ‏409 לחפיפה (הבקשה תקינה אבל מתנגשת במצב הקיים), ‏404 למשאב שלא נמצא. ב-POST חדר שלא קיים מחזיר 400, כי זו שגיאה בשדה בגוף הבקשה ולא ב-URL.
- **שגיאות בפורמט ProblemDetails**, שהוא הסטנדרט של ASP.NET. ללקוח יש פונקציה אחת (`toErrorMessage`) שהופכת כל שגיאה להודעה קריאה. גם JSON פגום מחזיר 400 עם הודעה ברורה ולא תשובה ריקה.
- **זמנים כשעון מקומי ללא אזור זמן** (`2026-11-24T09:00:00`). זה הפשוט ביותר למערכת של משרד אחד. ההנחה מתועדת בקוד.
- **בחלונית יש תאריך אחד ושתי שעות**, ולא שני שדות תאריך ושעה מלאים. כך אי אפשר לשבור את חוק "אותו יום" מהממשק. השרת עדיין בודק את החוק, כי ה-API יכול לקבל בקשות גם שלא מהממשק.
- **ולידציה בצד הלקוח מינימלית** (שדות חובה בלבד). השרת הוא מקור האמת, והודעות השגיאה שלו מוצגות בתוך החלונית.

## 3. בדיקות

**בוצעו:**
- **בדיקות יחידה** (xUnit, ‏`server/MeetingRooms.Api.Tests`, ‏19 מקרים): מיון לפי שעת התחלה וסינון לפי חדר ויום, הזמנות צמודות (10:00/10:00) שאינן חופפות, חמישה סוגי חפיפה (התחלה בפנים, סיום בפנים, מוכלת, מכסה, זהה), אותה שעה בחדר אחר, שדות חובה (null, ריק, רווחים), סיום לפני ההתחלה או שווה לה, הזמנה שחוצה יום, חדר לא קיים, זמנים חסרים, ביטול שמשחרר את הזמן, ו-50 בקשות מקבילות לאותו זמן שרק אחת מהן מצליחה.
- **בדיקה ידנית של ה-API עם curl**: כל קודי הסטטוס בטבלה למעלה, כולל JSON פגום ופורמט תאריך שגוי.
- **בדיקה ידנית מקצה לקצה בדפדפן**: הוספה, מיון, הודעת חפיפה, הודעת ולידציה וביטול.

**היו מתבצעות עם עוד זמן:**
- בדיקות אינטגרציה ל-API עם `WebApplicationFactory<Program>`, שבודקות קודי סטטוס וגוף ProblemDetails.
- בדיקות יחידה בלקוח ל-`toErrorMessage` ול-`toDateString`, ובדיקת קומפוננטה לחלונית.
- בדיקת E2E אוטומטית (Playwright) לתרחיש המלא.

## 4. מה לא הספקתי ומה הייתי עושה עם עוד שעתיים

- אחסון קבוע (SQLite עם EF Core), כשבדיקת החפיפה וההוספה מתבצעות בטרנזקציה אחת.
- בדיקות האינטגרציה וה-E2E שהוזכרו למעלה.
- עריכת הזמנה קיימת.
- תמיכה באזורי זמן (שמירה ב-UTC עם אזור זמן לכל חדר).
- הזדהות משתמש, כך ששם המזמין יילקח מהמשתמש המחובר ורק הוא יוכל לבטל.
- תצוגת ציר זמן של היום, שמראה זמנים פנויים.
